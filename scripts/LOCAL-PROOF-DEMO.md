## 1. Verified repository state
The current repository is a TypeScript reference core. Its root `package.json` defines:
- `npm test` → `node --test tests/*.test.mjs`
- `npm run check` → informational echo only; it is not a typecheck.

The repository does **not** currently declare Miniflare, Wrangler, a Worker entry point/configuration, or a `SafetyInterlock` implementation. The source includes `src/constitution.ts` (`evaluateConstitution`), `src/decision-lifecycle.ts`, `src/hmac-passport.ts`, and `src/pioneer/compose.ts` (`pioneerDecisionGate`). These are not, by themselves, an HTTP Worker that can return a real 403.

**Therefore this document does not claim that a local E2E 403 demo is currently runnable.** Do not create a hand-written 403 or a fabricated evidence file and present it as proof of the production interlock.

## 3. What is required to make the requested Miniflare 403 demo real
Before writing a runnable harness, bring the actual Worker implementation into this repository or identify its authoritative repository and immutable commit. Required inputs:

- Worker entry point and route that receives the agent proposal.
- Actual `SafetyInterlock` module and the exact call site immediately before protected tool execution.
- Request/response contract, including the expected denial status and stable reason code.
- Miniflare-compatible bindings and test fixtures (including secrets represented only by local test values).
- A deterministic deny case (for example, an action explicitly forbidden by the active constitution) and an allow control case.
- Evidence schema and signing/verification function used by the real Worker.

Then add Miniflare as a pinned development dependency, configure the local Worker with the same module entry point and test bindings, and write an integration test that invokes the Worker through Miniflare's `dispatchFetch`. The test must assert: (1) the request reaches the real SafetyInterlock, (2) denial returns the agreed 403 response, (3) the protected tool was not invoked, and (4) the JSON evidence is generated by the real evidence module and verifies successfully. A second allow-case should prove the harness is not simply hard-coded to deny every request.

## 4. Evidence JSON — acceptance contract, not a fabricated sample
The eventual demo should write a file such as `artifacts/local-proof-evidence.json` containing, at minimum:

- schema/version and `demo_only: true`
- repository, commit SHA, runtime and test-run identifiers
- request/decision identifier, tenant and agent test identifiers
- action and policy/constitution version
- decision (`DENIED`), HTTP status (403), stable reason code
- timestamp and hashes of the canonical request/context and evidence manifest
- signature algorithm, key identifier and verification result (never include secret keys)
- explicit statement that this is local Miniflare evidence, not a Cloudflare production result

The test must create this file from the actual Worker response and actual signing code, then independently verify it. A static JSON file or a JSON assembled by the demo script without invoking the interlock is not acceptable evidence.

## 5. Investor demo run-of-show (once the Worker adapter exists)
1. Show the commit SHA and local runtime; disconnect/disable external network access.
2. Start Miniflare using the pinned local configuration.
3. Submit the deterministic forbidden-action request.
4. Show the actual Worker response: HTTP 403, reason code and no protected-tool invocation.
5. Open the generated evidence JSON and run the independent verifier.
6. Submit the allowed control request and show the distinct authorized result.
7. State clearly: “This demonstrates the local test harness. Cloudflare staging/production E2E and any Bitcoin/OpenTimestamps anchor remain separate validations.”

## 6. Safety rules
- Never deploy, edit Cloudflare bindings/secrets, or call external timestamp services from this offline demo.
- Never use production credentials in local fixtures.
- Never label a mock, unit test or manually assembled JSON as E2E proof.
- Preserve the existing working Worker and its bindings; integrate through a separate test adapter/branch only after its source and contract are confirmed.
